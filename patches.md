## 1. OMP provider

- OMP is an independent provider instance with display name `OMP` and executable `omp`.
- It shares the Pi driver, without overwriting a user's existing Pi configuration.
- OMP is not a default instance; it is added per machine in Settings → Providers (`OMP_PROVIDER_INSTANCE` in `contracts/src/ompProvider.ts`), and only the Mac has it. Settings that omit `providerInstances` get none, as upstream. Until 2026-10-25 the fork added OMP to such settings, so agent-hub and agent-fr, which have no `omp`, showed `OMP CLI (omp) is not installed`.
- The creation wizard offers Pi and OMP separately, with independent drafts. It keys choices and drafts by driver kind, so `providerInstancePresets.ts` lists OMP under its own key `omp` and maps it back to the Pi driver and the `omp` defaults on save; `AddProviderInstanceDialog.tsx` imports it under upstream's `providerClients` name.
- OMP shows its own π mark and gradient from omp.sh instead of Pi's glyph. Instances share the `pi` driver, so `providerIconKind` treats a Pi instance whose name starts with "OMP" as OMP; it lives in `packages/contracts/src/ompProvider.ts` with the default instance and `OMP_ICON_URL`. Web's `ProviderInstanceIcon` is given every instance's name and checks it there; its `OmpIcon.tsx` shares the root `vite.config.ts` raw-color lint exemption with upstream's brand icon files. Mobile's `ProviderIcon` is handed only a driver and an icon URL, so the Pi driver stamps `OMP_ICON_URL`, an SVG data URL, on such an instance's snapshot (`ompInstanceIcon` in `rpcDialect.ts`, same name rule), and every mobile surface that passes the provider's icon draws the mark. Surfaces that pass only the driver (usage, environment provider lists) still show Pi, and so does a server without this patch. Web provider update prompts (the update-run toast, sidebar pill, Update all summary and tooltip, the sidebar's update-everything confirmation; upstream dropped the launch-time toasts on 2026-10-22) group and name by `providerUpdateKind` and `providerUpdateName` (`apps/web/src/components/providerUpdateName.ts`), so OMP updates are labelled OMP and do not collapse into Pi's. Upstream code that builds a provider list from `PROVIDER_DISPLAY_NAMES[driver]` names OMP as Pi and every ACP agent as ACP Registry; route it through `providerUpdateName` (Settings → Providers' `Could not update` toast does).
- OMP JSONL dialect adapts command discovery, correlated prompt admission/completion, background settlement, queue state, and before-user branch semantics. Pi remains a passthrough.
- The T3 MCP extension's `$skill` input hook reads the skill file from `sourceInfo.path` (Pi) or `path` (OMP `getCommands()`), and skips a skill command with neither. Reading only `sourceInfo.path` threw on OMP, reported as `pi-t3-mcp-extension failed during input`, whenever a message carried a selected skill chip. OMP `18.7.0` and `18.8.7` share this shape.
- Upstream now owns the completed-probe model-list replacement for both Pi and ACP Registry in `shouldRetainMissingProviderModels` (`apps/server/src/provider/ProviderRegistry.ts`); the fork no longer patches it. OMP rides the Pi rule because it shares the driver.
- The context window meter (Settings → General → Legacy features, off by default upstream) works for Pi/OMP in two more cases. Stop always terminates the Pi/OMP process, and finalizing after termination skipped `get_session_stats`, so every stopped turn lost its usage and a thread whose turns were all stopped never showed the meter. Stop now reads the stats right after the session-tree refs, before terminating, and skips the read when the refs read already failed, so a hung process does not wait twice. OMP's `message_update` carries cumulative usage only on `message.usage`, while the adapter reads Pi's top-level `usage` (Pi `0.84.2`+), so the meter never moved during an OMP turn; the OMP dialect now lifts it. OMP `18.8.9`'s Anthropic stream sets usage at `message_start`; providers that report usage only at response end move the meter once per assistant message. The lift was checked against the installed binary, not a recorded live stream.
- OMP's `todo` tool shows as the thread's todo list, like Claude's TodoWrite. A successful call reports every phase in `result.details.phases`; the Pi adapter mirrors it into the turn's `todo_list` plan (`ompTodoSteps` in `packages/provider-pi/src/server/rpcDialect.ts`). A `view` call or a failed call leaves the list alone. `in_progress` runs, `completed` and `abandoned` are done, `pending` and `blocked` wait, and tasks carry their phase name when there is more than one phase. Pi has no todo tool, so nothing changes there. Shape checked against OMP `18.9.2` source.
- OMP mounts MCP and rarely-used tools as `xd://` devices (`tools.xdev`): the model calls them with `write xd://<tool>` and the tool's arguments as content, so every such call showed as a `file_change` to a file that never existed (agent-channel #74). The OMP dialect renames `tool_execution_*` events for a `write` whose path is `xd://<name>` to that tool with the parsed content as its arguments (`ompDeviceCall` in `rpcDialect.ts`), so they show as tool calls and MCP results unwrap like a directly mounted `mcp__` tool. `xd://<tool>/<topic>` and a bare `xd://` stay as they are. URL shape checked against the OMP `18.14.0` binary.
- OMP's local models put their words in reasoning and emit a blank text block between thinking and each tool call, so a handoff from OMP carried one empty `Historical assistant` entry per step. Upstream's `historicalMessage` (`packages/provider-core/src/server/handoffBudget.ts`) now drops a whitespace-only `assistant_message`, for every provider; reasoning and dynamic tool calls stay out of handoffs as upstream decided (Jason, 2026-10-30, agent-channel #74). Covered by `ContextHandoffBudget.fork.test.ts`.
- Thinking streams live for models that think in one unbroken paragraph. Paragraph streaming (the default `responseStreamingMode`) held reasoning until a blank line, list item or closing fence, so the local models behind OMP showed no thought until it ended, even though the Pi adapter received every `thinking_delta`. `apps/server/src/orchestration-v2/assistantStreaming.ts` now passes reasoning's whole text on the existing 400ms throttle for every provider; assistant text keeps paragraph buffering, and `turn` mode still streams nothing. Cost: every snapshot the filter passes is stored as a durable `turn-item.updated` row holding the item's full text (upstream #23365), so reasoning now writes one row per 400ms while it streams, for every provider, not only OMP; the growth has not been measured here. Upstream PR #24700 bounds the rows for long items but keeps paragraph buffering, and edits the same lines; revisit this branch when it lands. The missing live thought is reported on #23365 (comment of 2026-10-26).
- Compatible protocol was inspected from installed OMP `18.7.0`; tests cover these adaptations. No model-generation request was used during verification.

## 3. Local ACP commands in provider updates

- A local ACP command (`source: "local"`) has no registry entry, so its snapshot version is the `agentInfo.version` it reports in ACP `initialize`. Registry agents keep the registry's version.
- Two hidden settings opt it into the existing update flow: `npmPackageName`, used only to look up npm `latest`, and `updateCommand`, an executable and arguments the runner spawns with the instance's environment under a `local:<instanceId>` lock. Without them nothing changes. The command must not prompt: it has no terminal and the runner gives it five minutes.
- After a successful update, upstream's `ProviderRegistry.refreshAfterUpdate` (#14319) calls `invalidateCaches` on every enabled instance of that driver and probes it fresh. The fork only supplies the ACP driver's `invalidateCaches`, which drops its probe cache, so the next probe reads the new version and models; updating one local ACP command also re-probes the other ACP instances. The ACP readiness check repeats the last probed version so health refreshes neither blank it nor miss the probe cache.
- Updates are still started by a person (toast, instance card, mobile); the server never runs them on its own. Web update prompts key each ACP Registry instance by its instance id and name it by its display name (`providerUpdateKind`/`providerUpdateName`, section 1), so Kimi, Qoder and Perch each get their own prompt and one-click update. Until 2026-10-28 they were keyed by driver: only one ACP agent's update was offered, named ACP Registry, and while several had one, its one-click update was refused because their update commands differ. `ProviderUpdateLaunchNotification.logic.fork.test.ts` covers it.
- The maintenance capabilities, the probed version and the npm version advisory live in `packages/provider-acp-registry/src/server/localCommandUpdates.ts`; `driver.ts` calls it from its snapshot pipeline. The advisory is added to a background probe's result before the snapshot permit is taken, so the npm lookup never holds up live command and configuration updates.

## 4. Manual context compaction for ACP agents

- The ACP Registry adapter exposes the existing compaction operation so the context meter can execute an agent's advertised `compact` command. The UI still offers the button only when the agent lists that command, and disables it during a running turn. This also applies to local commands such as `perch-acp`.
- kimi-code (2.3.1) answers `/compact` the moment its compaction starts in the background. A message sent before it ends is queued by kimi's engine and answered at once, so T3 closed the run with no output while kimi ran that turn unseen and dropped its updates (agent-channel #30, 2026-10-24). `packages/provider-acp-registry/src/server/backgroundCompaction.ts` wraps every registry runtime: when a `/compact` prompt reports `Context compaction started`, the prompt stays open until kimi's `Compaction completed.` or `Compaction cancelled.` notice, so the next message waits in T3's queue and the notice shows in the compaction turn. Stop ends the wait as cancelled. kimi sends nothing when the compaction request fails, so the wait gives up after 15 minutes. It keys on kimi's English wording and needs revisiting if kimi changes it; agents that compact before answering are unaffected. Covered by `backgroundCompaction.fork.test.ts`.

## 5. MCP approval codes and remote agent sign-in

- `t3 auth pairing create` takes `--session-ttl <duration>` (how long MCP sign-ins approved with the code last; upstream fixes 30 days and issues no refresh tokens) and `--reusable` (approvals do not spend the code until its own `--ttl` ends or it is revoked). Either flag makes an MCP-only code: device pairing refuses it, so a reusable code can never pair unlimited clients. Plain codes and Settings → Sharing & access codes are unchanged. The flags live in `apps/server/src/cli/authMcpApproval.ts`.
- The options live in the pairing link's `subject` (`mcp-approval;ttl=<ms>;reusable`, `apps/server/src/auth/mcpApprovalCode.ts`) rather than new columns, because a fork migration would collide with upstream's numbered migrations. `McpApprovalCodes.ts` wraps upstream's `PairingGrantStore` layer, and EnvironmentAuth's layer provides it instead: the wrapped `consume` refuses MCP-only codes, and `McpApprovalCodes.use` reads a code for MCP approval without spending a reusable one. `PairingGrantStore.ts` is upstream's. The session TTL travels in McpOAuth's pending authorization code to `issueMcpClientSession`.
- The `/connect-agent` page no longer redirects straight to a loopback callback after approval. It shows **Continue on this computer** and **Copy link**, because an agent such as mcp-remote on the Grok Bot's machine listens on its own `localhost`, which the approving browser cannot reach. Denials and https callbacks still redirect immediately.
- Covered by `apps/server/src/auth/McpOAuth.fork.test.ts` ("an MCP approval code sets the sign-in lifetime, may be reused, and never pairs a client").
- Upstream: Ideas discussion #22215 (the copyable callback link) and a comment on #19460 (`--session-ttl`, `--reusable`), both 2026-10-20.

## 6. Device sign-ins renew while they connect from their device

- Upstream fixes direct-paired sessions (bearer tokens and browser cookies, over LAN or Tailscale) at 30 days. T3 Connect does not change that: its clients get one-hour DPoP sessions minted again through the cloud account (`EnvironmentAuth.ts`), while a device paired directly to the same server still expires after 30 days. So this patch is not a stand-in for T3 Connect, and it stays now that fork builds carry the T3 Connect configuration (2026-10-30). The fork renews the stored session: when a session connects with 29 days or less left, `expires_at` moves to now + 30 days (`apps/server/src/auth/sessionRenewal.ts`). It renews in `markConnected` (alongside `lastConnectedAt`), in the WebSocket ticket handler for browser cookies, and in `awaitInvalidation`, which wakes an open connection when its session falls due instead of sleeping until the deadline read at connect time.
- Renewing because a credential is in use let a copied token live forever (sg448 on discussion #18003, 2026-10-27; the reason Julius gave on 2026-10-06 for dropping upstream #16274). Tailscale renews nothing for use either: a node key expires and the node proves itself again (KB 1028; headscale `machineKeyMismatch`). So each call site passes a `RenewalCheck` built from the connection's request (`TailscalePairing.renewalCheckOf`), asked only once a renewal is due, at most once a day per session. A `tailscale:<StableID>` session renews only when `tailscale whois` on the request's source (patch 7's `resolveSource`, so Serve's `X-Forwarded-For` counts) names that node. A `one-time-token` session (a typed or scanned code) from the owner's untagged, unblocked node, on a host with pairing on, takes that node's subject in the same guarded `UPDATE`, so the next renewal and patch 7's revocation block apply to it. Everything else never renews: LAN and local connections, other nodes, `cli-issued-session`, `administrative-bootstrap`. Those keep working until their deadline, after which the resolver pairs again over Tailscale or asks for a code (owner decision, 2026-10-27). Whois is never run per request, because learned routes reuse a credential over the LAN.
- `SessionStore.verify` checks the stored `expires_at` instead of the token's `exp` claim, and returns it and the stored subject. Renewing the row alone would not help: a bearer token is rejected at its claim before it can get a WebSocket ticket, and an adopted session's token still carries `sub: one-time-token`. The claim is still decoded and validated. Revocation is checked before expiry, so a signed-out device hears so after its deadline too.
- Clients learn why a credential was refused: `EnvironmentAuthInvalidReason` adds `session_expired` and `session_revoked` (`serverAuthCredentialReason` reads the SessionStore error), and patch 7's pairing endpoint answers `tailscale_pairing_revoked` for a blocked node. Client-runtime shows "The sign-in expired. Pair this device again." or "This device was signed out." (`connection/sessionEndedText.ts`, a display file), including when the resolver's or onboarding's Tailscale pairing is refused for a blocked node. `isRejectedCredentialReason` keeps the DPoP retry in `environmentHttpAuth.ts` and the pull request diff check treating the new reasons as a refused credential.
- Browsers drop a cookie at the `Expires` it was set with, so the ticket handler renews first and then re-sets the `t3_session_*` cookie with the stored expiry (`renewBrowserSessionCookie` in `auth/authHttpFork.ts`).
- Never renewed whatever the check says: revoked or expired sessions (the SQL update repeats both guards and the old subject, so a revocation that races a renewal still wins), `mcp-client` sessions (their lifetime comes from `--session-ttl`, patch 5), DPoP sessions, and sessions issued shorter than 30 days.
- No migration; only the existing `expires_at` and `subject` columns change. The upstream code touched is the expiry and subject in `verify`, one line in `markConnected`, the sleep in `awaitInvalidation`, the `renewIfDue` service method (passed through from `sessionRenewal.ts`), the renewal check in `ws.ts` (with `TailscalePairing.layer` provided to `Ws.layer` in `server.ts`), `serverAuthCredentialReason`, the two reason literals and the helper in `contracts/environmentHttp.ts`, the reason checks in `environmentHttpAuth.ts`, `pullRequestDiffHttp.ts` and client-runtime `errors.ts`, and one line in the ticket handler.
- Covered by `apps/server/src/auth/sessionRenewal.test.ts` (renewal, adoption, refusal reasons) and the "Tailscale session renewal" cases in `TailscalePairing.test.ts` (same node, other node, LAN, tagged, other owner, blocked, pairing off), plus client-runtime `errors.fork.test.ts` and `resolver.fork.test.ts`.
- Upstream: Ideas discussion #18003 (formerly issue #13055) asks for this; upstream `f88b33a16d` still fixes sessions at 30 days. The earlier design, renewing on any use, is posted there (comment of 2026-10-26), and so is this one (2026-10-27).

## 7. Tailscale pairing, tagged MCP sign-ins and tailnet discovery

- Off by default; on for agent-hub (its drop-in, since 2026-10-20), agent-fr (its start script) and the Mac (the login shell profile, section 17, since 2026-10-27). `T3CODE_TAILSCALE_PAIRING=true` turns on device pairing and discovery; `T3CODE_TAILSCALE_MCP_TAGS="tag:x=<access>,…"` turns on MCP approval for those tags. Both are read in `apps/server/src/auth/TailscalePairing.ts`, an env var rather than a `ServerConfig` field so upstream's config and its tests stay untouched.
- The tailnet identity only replaces the pairing code. `POST /api/auth/tailscale-pairing` hands the requesting device a one-minute pairing code (subject `tailscale:<StableID>`, label = machine name, standard scopes), which the client redeems through the existing `/oauth/token` or browser-session exchange, so patch 6 renewal and every later auth and Origin check apply unchanged. Web pages can reach tailnet addresses and a standard session runs terminals, so the endpoint also checks Origin and requires the Host to be an IP, a single-label name or a MagicDNS name: without a code to guard it, DNS rebinding would otherwise pass as same-origin.
- Identity comes from `tailscale whois` on the TCP peer (`request.source.socket.remoteAddress`, never a header). Tailscale Serve reaches the server from the host itself (agent-hub: its own tailnet IP, not 127.0.0.1), and whois on a local address names the host and its owner, so a local peer is never looked up: only Serve's `X-Forwarded-For` is, plus `Tailscale-User-Login` for device pairing. Serve (`ipn/ipnlocal/serve.go`, `httputil.ReverseProxy.Rewrite`) strips client-sent copies of both and omits the user for tagged nodes, funnel and local traffic. Any local process can claim to be Serve; the host is trusted, and no other reverse proxy may front the server while this is on.
- Devices: untagged, owner equal to the host's (`status --json` Self → User), host not tagged. MCP: tagged nodes whose tags are listed get the lowest listed access, only for loopback redirect URIs, so a code issued at `/oauth/mcp/authorize` without the approval page can only reach the requesting machine. Its session subject is `mcp-client:tailscale:<StableID>`; `mcpClientSubject.ts` is now the single check that confines MCP sessions to `/mcp` (EnvironmentAuth's audience check, `authenticateMcpClient`, patch 6's renewal exclusion), and a test fails if the audience check goes back to an exact match.
- Revocation without a migration: a node is blocked when its newest revocation is later than its newest session under that subject. Revocations made by issuing a replacement session (same instant as the replacement's `issued_at`, any subject) do not count, and a node with several clients is blocked by revoking any of them. `t3 auth tailscale blocked|unblock` lifts a block by inserting an already-expired session row, which can never authenticate.
- Discovery: `GET /api/tailnet/servers` (orchestration:read) probes the owner's online, untagged, non-phone peers at `http://<IPv4>:3773` (and the server's own port) and `https://<MagicDNS>/` for `/.well-known/t3/environment`. One `tailscale status --json` read serves a discovery, and a successful answer is shared for 30 seconds (`Effect.cachedWithTTL`; an unreadable status is not shared, but still answers an empty list over HTTP). Clients ask every connected environment (`client-runtime/src/connection/tailnetDiscovery.ts`). Mobile asks in the background while the app is in the foreground (`watchTailnetDiscovery`): each connected environment when it connects, then every 10 minutes, backing off 1, 2, 4… minutes (at most 10) after a failure, so app start, foreground and reconnects cannot bypass the backoff. A list counts only while its environment is connected and its last success is under 20 minutes old; a stale list is withdrawn on its own wake-up without a request. In the background no timer is set at all: a due ask must not wake a loop that cannot send it, so nothing runs until the app comes back. Home (`TailnetServerHomeRows`, including both empty states, which would otherwise never start discovery), the add screen and both environment lists show the answer; the add screen says whether nothing was found or no server could be asked. A tap pairs only if the address still answers with the suggested environment id (`suggestedEnvironmentId`, unlike `expectedEnvironmentId` it keeps the saved-address check). That id is readable by anyone who reaches the descriptor (the Mac listens on all interfaces), so it stops a stranger who rerouted a 100.x address, not someone who copied the id. Tailscale Android keeps its device list to itself (LocalAPI only in-process, no web client on Android, no exported provider), and the Tailscale API's OAuth needs a credential that can read the device list, so the earlier OAuth client in SecureStore was dropped on 2026-10-27 (agent-channel #61).
- First server (agent-channel #73): a build can set `T3CODE_MOBILE_TAILNET_ENTRY_URLS` to comma-separated `https://host[:port]/` entries (`apps/mobile/src/connection/tailnetEntryUrls.ts`; any path, credentials, query, fragment, whitespace or empty port fails `app.config.ts`, so the build fails; the raw text is checked before `new URL`, which would normalize `https:host`, `/a/..` or an embedded tab into a valid entry). Once saved environments have loaded and there are none, the add screen probes them every 15 seconds and lists the ones that answer under 可能的 T3 伺服器; a tap pairs without a code. HTTPS only, because only a certificate keeps the name honest when Wi-Fi DNS, Private DNS or another VPN can answer for it. The probe, the pairing request and the token exchange use `expo/fetch` with `redirect: "manual"` (`tailnetEntry.ts`): React Native's Android fetch always follows redirects, and a redirect from a misconfigured proxy could carry the exchange's `subject_token` to another host. A 3xx fails as 無法連到這個伺服器. Android only. The owner's build sets `https://agent-hub.tailb20be.ts.net/` (Android APK from source). A phone with no environment can also type a machine name: `buildPairingUrl` turns a single-label host into `http://<name>:3773/`.
- Clients: an address without a code pairs over Tailscale (`resolveCodelessPairingEndpoint` in `packages/shared/src/remote.ts`, onboarding in client-runtime, mobile `buildPairingUrl`). Only a refusal (or a server without the endpoint, a 404) asks for a code; a signed-out device, a redirect, a network failure and a failed exchange each keep their own message (`pairingFailureText.ts`); a rejected or missing saved bearer credential tries it before failing (resolver bearer broker); the web primary tries it before the pairing screen when the server is `remote-reachable` only, so loopback servers make no extra request.
- Upstream code touched: the forbidden reason literal, the `TailnetServer` schema and two endpoints in `contracts/environmentHttp.ts`; two `.handle` lines in `auth/http.ts`, whose handlers live in `auth/authHttpFork.ts` (the service is optional, so routes built without it refuse); one `Layer.provide` in `server.ts`; the authorize redirect in `mcpOAuthHttp.ts`; `McpOAuth`'s pending-code session options and `approveOverTailscale` (built on `approveMcpSignIn` in `TailscalePairing.ts`); `issueMcpClientSession`'s optional subject; the bearer broker, onboarding, web `auth.ts`, the add environment dialog (`AddEnvironmentDialog.tsx`, `parseRemotePairingFields` in `ConnectionsSettings.logic.ts`), mobile pairing screen and `buildPairingUrl`, and the web test helper.
- `packages/tailscale/src/tailnetIdentity.ts` reads host identity, `whois` and peers; `tailscale.ts` only allows the `whois` subcommand and exports `readTailscaleOutput` for it.
- Covered by `TailscalePairing.test.ts`, `TailscaleMcpApproval.test.ts`, `packages/tailscale` identity tests (`tailnetIdentity.test.ts`), client-runtime onboarding, resolver and `tailnetDiscovery` tests, and web `authBootstrap.test.ts`.

## 11. Ephemeral threads

- A thread is ephemeral from `thread.create` on and never switches. It lives in No project, runs on the OMP instance with a model whose `baseUrl` is loopback (`ServerProviderModel.local`), and nothing of it is kept once it ends: deleted by the user, idle for 60 minutes with no running run, its OMP process gone, or found at server startup. Stop aborts the run first; only a Stop whose abort fails ends the process, and with it the thread. The composer toggle (web `EphemeralDraftToggle.tsx`, mobile `EphemeralThreads.tsx`) appears only for a No project draft on OMP with a local model; `canStartEphemeralThread` in `contracts/src/ephemeralThread.ts` decides for both clients, and the server checks again.
- Policy sits in one dispatch wrapper, `server/src/orchestration-v2/EphemeralThreads.ts`, provided through `ThreadManagementService`. Commands are allow-listed: anything not in `UNCHECKED_COMMANDS` or `CHECKED_COMMANDS` is refused, so a command upstream adds later is refused on an ephemeral thread until someone decides otherwise. Refused: fork, handoff, merge back, context transfer, archive, title regeneration, branch or folder changes (the launch may record the Scratch folder it made, once), scheduled or agent-sent messages, and any model outside the thread's OMP instance or not local. MCP never sees them (`mcp/hideEphemeralThreads.ts`), thread search skips them and the message search index never takes their text (`messageSearchIndex.ts`; FTS5 segments keep deleted text until a merge), guest shares are refused in `GuestShareDecider.ts` because guest commands are dispatched without the wrapper, the agent awareness relay sends fixed text, and the title is the first line of the first message with no title model.
- Purge deletes every row naming the thread from columns found in the live schema (`thread_id`, `source_thread_id`, `target_thread_id`, `child_thread_id`, plus `stream_id`/`aggregate_id` in tables with `aggregate_kind = 'thread'`), so tables upstream adds are covered without edits. It removes attachments, terminals and the Scratch folder first, aligns `orchestration_v2_projection_metadata.last_sequence` (otherwise `t3 doctor` refuses to compact), then runs `wal_checkpoint(TRUNCATE)`. The Scratch folder name carries no words from the message.
- `PRAGMA secure_delete = ON` is set for the whole connection in `persistence/Sqlite.ts`. Turning it on only while purging is not enough: streamed message updates leave old row versions in free pages (measured: 30 marker remnants of 40 updates). Cost on a 3.6 GB copy of real data, 30 rounds of streamed writes: median +5.4%, mean +4.7%, WAL bytes +7.4%. Index pages can still hold the bare thread id, never text; only `VACUUM` clears those.
- A client that resumes a shell subscription from its in-memory cursor would miss a purged thread's `thread.deleted`, so `ws.ts` sends a fresh snapshot when the resume crosses a purge (`replayCrossesPurge`). `ThreadFind`'s per-thread scan cache is evicted on purge; its one-minute text cache is not keyed by thread and simply expires.
- OMP (`provider-pi/src/server/ephemeral.ts`) launches like any OMP thread, with every tool, its extensions, plugins and the user's own MCP servers, except: `--session-dir` points at `.omp-sessions` in the thread's Scratch folder, `--no-title`, no T3 MCP, and a settings overlay with `disabledProviders` for every hosted provider, `enabledModels` for the local ones and OMP's memory off, since it writes what it learns to disk. Jason decided on 2026-10-25 that an ephemeral thread keeps no record but otherwise uses OMP normally. Until then it ran `--no-session` with a seven-tool allowlist, fetch, browser and GitHub off, `write`/`edit` held to the Scratch folder and only listed extensions, and the local model could not answer a weather question. `disabledProviders` filters OMP's model registry, so the vision fallback cannot reach a hosted model either; `enabledProviders` does not restrict models (OMP 18.12.6). A throwaway `--no-session` process with the same launch args lists the models before the real one starts, so providers that extensions or other config sources add are disabled too.
- Purge removes the Scratch folder, and with it the session files, subagents' included. In an OMP 18.12.6 RPC run under a scratch `HOME` with a loopback model, the prompt and reply text appeared only in that session file: no `history.db` or `stats.db` was written. Outside it OMP left no text, only a pointer file in `~/.omp/agent/custom-session-files/` holding the session file's path, a `Session exit recorded` line in its log and an empty lock named by the session id; these stay. Files a tool writes outside the Scratch folder are not tracked and stay too, because nothing tells them apart from files the user already had.
- Clients keep nothing on the device: client-runtime's shell and thread caches skip ephemeral threads, web drafts and the prompt stash leave them out of `localStorage` (the stash refuses), and mobile keeps their drafts and queued messages in memory (`state/ephemeral-thread-keys.ts`, kept apart from the shell atoms so storage modules and their tests do not load them). Deleting always confirms that the conversation is erased and cannot be recovered, with no undo. Actions the server refuses are left out where the UI already decides what to show: an ephemeral session reports no fork, rollback or provider handoff (`PiEphemeralCapabilitiesV2`), so both clients drop the fork button and lock the provider; web's thread menus drop settle, title regeneration and archive, the sidebar row's hover action deletes instead of settling (and a settle sweep skips the row), the composer offers only the thread's runtime mode and local models, and rewind and the settle shortcut are off; mobile's row menu keeps arrange, rename and delete, swiping deletes, and the thread settings sheet lists only local models and the current runtime mode. When one ends, web shows a toast and leaves the thread; mobile's thread screen says the conversation ended (`endedEphemeralThreadKeysAtom`, memory only).
- The window title gains （無痕對話） and never names the thread (web `document.title`, desktop `page-title-updated`), and web notifications and iOS Live Activities show the same fixed text. Android adds `FLAG_SECURE` while one is on screen (`T3NativeControls.setSecureWindow`, reference counted) and `IME_FLAG_NO_PERSONALIZED_LEARNING` to the composer. iOS has no keyboard flag for this, and macOS `setContentProtection` is not used.
- Out of scope: oMLX's SSD prompt cache, Voco and Vocotype history, the macOS account, and disk encryption.

## agent-hub headless server (2026-10-14)

- The server runs on the owner's dev machine (`agent-hub`, PVE CT, Ubuntu 24.04 x86_64) from this fork's source at the same commit as the Mac nightly client. The client/server gate is the integer `ORCHESTRATION_PROTOCOL_VERSION` compared for equality (`packages/contracts/src/environment.ts`, enforced in `apps/server/src/ws.ts` and `packages/client-runtime/src/connection/compatibility.ts`); semver strings only drive update notices. Installing upstream's `t3` from `t3.codes/install.sh` would put a different version line on the host, so a source build from the fork is what keeps the gate matched.
- `t3 service install` cannot be used for a fork build: `BootService` downloads and validates a pinned release archive for its own version from GitHub Releases (`packages/shared/src/cliRelease.ts` default base URL), and this fork publishes no releases. A hand-written systemd unit is used instead.
- Unit: `/etc/systemd/system/t3code.service`, a **system** unit modeled on the machine's existing `takopi.service` (`User=jason`, `WantedBy=multi-user.target`, `After=network-online.target tailscaled.service`), not a user unit, so it needs no lingering. `ExecStart` runs `node <repo>/apps/server/dist/bin.mjs serve --host <tailnet IP> --port 3773 --no-browser`; the server binds only that tailnet address, never `0.0.0.0`. `PATH` carries `~/.local/bin`, `~/.opencode/bin` and `~/.kimi-code/bin` so provider CLIs resolve, and `NODE_OPTIONS` raises the heap. The unit header carries the rebuild command.
- Install on the host: `npm i -g pnpm@<version> vite-plus@<version>`, matching root `packageManager` and the `vite-plus` catalog entry (12.14.0 and 1.3.0 since 2026-10-22; an older global `vp` still runs but installs against the old version) (for `vp`), clone the fork, then the CI filtered install from `.github/workflows/release.yml`'s `build_bundle` job minus desktop: `vp install --filter=t3... --filter=@t3tools/web... --filter=@t3tools/scripts...`. This skips Electron and the mobile workspace; the resulting tree matches a full install on every structural count that matters.
- A full-monorepo `pnpm install` OOMs Node's default ~2 GB heap during resolution (exit 134). Set `NODE_OPTIONS=--max-old-space-size=8192` for install and build.
- Root `engines.node ^24.13.1` against the host's Node 26 is a warning only; there is no `engine-strict` and no `.npmrc`, so it is not fatal. The server's own range (`>=24.10`) is satisfied.
- The filtered install rewrites `pnpm-lock.yaml` on the host (it re-resolves `@pierre/trees`' `@pierre/theme` peer, swapping 1.1.0 and 2.0.0 between importers), leaving the checkout dirty. That drift blocks the next `git pull` whenever upstream touches the lockfile, so rebuilds start with `git checkout -- pnpm-lock.yaml && git pull --ff-only`. Never commit the host's lockfile back.
- Build: `vp run --filter @t3tools/web build`, then `node apps/server/scripts/cli.ts build` (tsdown bundle plus copying `apps/web/dist` into `apps/server/dist/client`). Run `node apps/server/dist/bin.mjs serve` afterwards; `t3 update` and the background service do not apply to a server run this way.
- `resource-monitor` needs a Rust toolchain, which the host lacks; it is resolved lazily and its absence degrades to a warning log, so it is simply not built. node-pty ships a linux-x64 prebuild, so no native compilation is required for this path despite the CI comment about Linux prebuilds.
- Pairing: `serve` prints a one-time pairing URL at boot; `t3 pair --label <name> --ttl <duration>` mints further links against the running server. Links are per device and one-time; already-paired devices reconnect without them.
- MCP for outside agents: `tailscale serve --bg http://100.95.60.35:3773`, run as the Tailscale operator `jason`, fronts the server at `https://agent-hub.tailb20be.ts.net` inside the tailnet only. T3 derives the OAuth issuer and resource from `Host` and `X-Forwarded-Proto`, so MCP clients see https; they need it, because Claude Code and mcp-remote refuse a plain-http token endpoint off localhost. `tailscale serve --https=443 off` removes it, and direct clients keep using the tailnet address. The Grok Bot (`lisky-box`, `tag:lisky`) connects through mcp-remote with the tailnet ACL letting it reach agent-hub. Approval codes come from `node apps/server/dist/bin.mjs auth pairing create` on the host, with patch 5's `--session-ttl` and `--reusable` when wanted.
- Patch 7 is on here (owner decision, 2026-10-20) through a second drop-in, `/etc/systemd/system/t3code.service.d/tailscale.conf`: `T3CODE_TAILSCALE_PAIRING=true` and `T3CODE_TAILSCALE_MCP_TAGS=tag:lisky=auto-accept-edits`, so the owner's devices pair without a code and the Grok Bot's next MCP sign-in needs no approval page. Delete the file, `systemctl daemon-reload` and restart to turn it off. To check it without issuing a code, POST `/api/auth/tailscale-pairing` with a foreign `Origin`: the 403 is the same either way, but the journal logs `Refused Tailscale pairing.` with reason `origin_not_allowed` when it is on (the host lookup through `tailscale` already passed) and `disabled` when it is off.
- Product usage events and T3 Connect relay traces are off (owner decision, 2026-10-21) through a third drop-in, `/etc/systemd/system/t3code.service.d/telemetry.conf`: `T3CODE_TELEMETRY_ENABLED=false`. The Mac's desktop app gets the same variable from the owner's login shell profile, which it reads at launch. Clients send no events of their own, so the two servers cover every surface. Check it in the server process's environment (`/proc/<MainPID>/environ` on agent-hub).
- The provider handoff budget is raised (owner decision, 2026-10-26) through a fourth drop-in, `/etc/systemd/system/t3code.service.d/handoff.conf`: `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP=48000` instead of upstream's default 16,000 (`packages/provider-core/src/server/handoffBudget.ts`, clamped to 1,024–64,000). The budget counts UTF-8 bytes, so a Chinese character costs about 3 and the default holds about 5,000 characters; on 2026-10-26 a Codex → Claude switch in one thread reported `Selected 11 intact items; omitted 12 items`, and the omitted items included the thread's long Chinese task message. The owner's login shell profile on the Mac sets it too, and the desktop app forwards it from there (section 17). agent-fr's start script passes it in its `env -i` list. That script parses its restart loop once, so stopping only the node process relaunches the server with the old variables (checked on 2026-10-26: the relaunched node lacked the new variable); restart the container from the host with `docker restart agent-fr` instead. The edited script lives in the container's writable layer, so recreating the container from its image drops the change. Live since 2026-10-26 on agent-hub (restarted, MainPID `107651`, the variable is in the process environment) and agent-fr (container restarted, the variable is in the node process environment, Mac curl HTTP 200); the Mac since `d150706dd0` (2026-10-26, the server process has `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP=48000`).
- T3 Connect (linked 2026-10-30) needs a listener on `127.0.0.1:3773`, since its tunnel dials loopback while the server binds only the tailnet address. `/usr/local/bin/t3-loopback-forward.mjs` listens on loopback only and connects to the server from `127.0.0.1`, so the server sees a loopback peer as upstream intends rather than its own tailnet node, which patch 7's `tailscale whois` would trust as the owner's. agent-hub runs it as `t3code-loopback.service` (`User=jason`); agent-fr's start script starts it once it has the tailnet IP and restarts it if it dies; replace that script with `mv`, never in place, because the running loop keeps reading the old file. Both servers now pass `--port 3773`: without a port, `serve` takes the first free one (`findAvailablePort` in `cli/config.ts`), and when the forwarder already held `127.0.0.1:3773` it moved to a random port, which a `docker restart agent-fr` on 2026-10-30 showed (it bound `:40393`, so tailnet clients and the tunnel both lost it). With the port fixed, the order does not matter: after the change both a container restart and a `t3code` restart bound `:3773` with the forwarder already running, and `t3 connect status` was reachable again. Binding the server to `0.0.0.0` instead would expose it on the LAN. `t3 connect status` on the host checks the tunnel end to end.
- To let a phone reach the **Mac** desktop-hosted server as a second environment, enable **Settings → Sharing & access → Network access** in the desktop app; that restarts it and rebinds off loopback, after which a pairing link can be created with the Mac's tailnet address.

## Android APK from source (2026-10-14)

- Upstream publishes no source-built sideloadable APK: `.github/workflows/mobile-android-apk.yml` only mirrors the Play Store APK (EAS-built, re-signed by Play) onto a rolling `android-nightly` prerelease. That mirror is English-only and its protocol version tracks upstream releases, so a fork APK must be built locally.
- Recipe on the Mac, from a committed checkout: `cd apps/mobile && APP_VARIANT=preview T3CODE_MOBILE_TAILNET_ENTRY_URLS=https://agent-hub.tailb20be.ts.net/ expo prebuild --platform android --clean --no-install`, then `cd android && APP_VARIANT=preview T3CODE_MOBILE_TAILNET_ENTRY_URLS=https://agent-hub.tailb20be.ts.net/ ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a`. The entry URL is agent-hub's Tailscale Serve, which a phone with no environment probes (section 7); Gradle reads `app.config.ts` again when it bundles, so both steps need it. `apps/mobile/android` is gitignored, so prebuild does not dirty the fork.
- Variant `preview` (`com.t3tools.t3code.preview`, label "T3 Code Preview") is chosen deliberately so a sideloaded fork build never collides with a Play install of `com.t3tools.t3code`. `development` is a dev client needing Metro and is not usable standalone.
- Signing: the RN template's `release` build type points at `signingConfigs.debug` (`app/debug.keystore`, password `android`), so the APK is installable by sideload but not Play-distributable. No new keystore is created and no fork source is modified.
- Toolchain: Gradle 9.4.1 requires JDK 17 or newer; the build was run with Temurin 25 (the default JDK 27 is too new). Set `ANDROID_HOME` and write `sdk.dir` into `android/local.properties`. The release task bundles the JS itself, so no Metro server is needed.
- `app.config.ts` reads the T3 Connect public configuration from the root `.env` into the APK's `app.config` asset (`extra`), not the Hermes bundle; check it there. Without that file every key in `scripts/lib/public-config.ts` is optional and the APK has no T3 Connect, which was the case until 2026-10-30.
- Output is a ~106 MB arm64-v8a APK at `apps/mobile/android/app/build/outputs/apk/release/app-release.apk`; install with `adb install -r`. The owner's phone is arm64 only. Without the flag Gradle builds a ~280 MB universal APK (arm64-v8a, armeabi-v7a, x86, x86_64); on 2026-10-26 a clean build on the owner's M5 Max (prebuild `--clean`, Metro cache cleared, cold daemon) took 267 s universal and 191 s arm64-only. Drop the flag only when an emulator or another device needs the other ABIs.
- The fork's `autoTranslate` Babel pass runs in the mobile build, so the APK follows the device language; verified rendering Traditional Chinese on a Poco F8 Ultra (Android 16) paired to the agent-hub server over the tailnet.
- Re-run `expo prebuild --clean --platform android` after pulling upstream before rebuilding, since the generated native project is not committed.
- A catalog-only change (`apps/web/src/locale/zh-TW.json`) does not invalidate the release JS bundle: Gradle's `createBundleReleaseJsAndAssets` tracks only mobile sources and reports UP-TO-DATE, and Metro's transform cache keeps the old translations.
