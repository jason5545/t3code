# Fork patches

Repository: https://github.com/jason5545/t3code
Upstream baseline: `b3d382e100` (merged 2026-10-25).

## 1. OMP provider

- OMP is an independent provider instance with display name `OMP` and executable `omp`.
- It shares the Pi driver, without overwriting a user's existing Pi configuration.
- OMP is not a default instance; it is added per machine in Settings → Providers (`OMP_PROVIDER_INSTANCE` in `contracts/src/ompProvider.ts`), and only the Mac has it. Settings that omit `providerInstances` get none, as upstream. Until 2026-10-25 the fork added OMP to such settings, so agent-hub and agent-fr, which have no `omp`, showed `OMP CLI (omp) is not installed`.
- The creation wizard offers Pi and OMP separately, with independent drafts. It keys choices and drafts by driver kind, so `providerInstancePresets.ts` lists OMP under its own key `omp` and maps it back to the Pi driver and the `omp` defaults on save; `AddProviderInstanceDialog.tsx` imports it under upstream's `providerClients` name.
- OMP shows its own π mark and gradient from omp.sh instead of Pi's glyph. Instances share the `pi` driver, so `providerIconKind` treats a Pi instance whose name starts with "OMP" as OMP; it lives in `packages/contracts/src/ompProvider.ts` with the default instance and `OMP_ICON_URL`. Web's `ProviderInstanceIcon` is given every instance's name and checks it there; its `OmpIcon.tsx` shares the root `vite.config.ts` raw-color lint exemption with upstream's brand icon files. Mobile's `ProviderIcon` is handed only a driver and an icon URL, so the Pi driver stamps `OMP_ICON_URL`, an SVG data URL, on such an instance's snapshot (`ompInstanceIcon` in `rpcDialect.ts`, same name rule), and every mobile surface that passes the provider's icon draws the mark. Surfaces that pass only the driver (usage, environment provider lists) still show Pi, and so does a server without this patch. Web provider update prompts (the update-run toast, sidebar pill, Update all summary and tooltip, the sidebar's update-everything confirmation; upstream dropped the launch-time toasts on 2026-10-22) group and name by `providerUpdateKind` and `providerUpdateName` (`apps/web/src/components/providerUpdateName.ts`), so OMP updates are labelled OMP and do not collapse into Pi's. Upstream code that builds a provider list from `PROVIDER_DISPLAY_NAMES[driver]` names OMP as Pi; route it through `providerUpdateName`.
- OMP JSONL dialect adapts command discovery, correlated prompt admission/completion, background settlement, queue state, and before-user branch semantics. Pi remains a passthrough.
- The T3 MCP extension's `$skill` input hook reads the skill file from `sourceInfo.path` (Pi) or `path` (OMP `getCommands()`), and skips a skill command with neither. Reading only `sourceInfo.path` threw on OMP, reported as `pi-t3-mcp-extension failed during input`, whenever a message carried a selected skill chip. OMP `18.7.0` and `18.8.7` share this shape.
- Upstream now owns the completed-probe model-list replacement for both Pi and ACP Registry in `shouldRetainMissingProviderModels` (`apps/server/src/provider/ProviderRegistry.ts`); the fork no longer patches it. OMP rides the Pi rule because it shares the driver.
- The context window meter (Settings → General → Legacy features, off by default upstream) works for Pi/OMP in two more cases. Stop always terminates the Pi/OMP process, and finalizing after termination skipped `get_session_stats`, so every stopped turn lost its usage and a thread whose turns were all stopped never showed the meter. Stop now reads the stats right after the session-tree refs, before terminating, and skips the read when the refs read already failed, so a hung process does not wait twice. OMP's `message_update` carries cumulative usage only on `message.usage`, while the adapter reads Pi's top-level `usage` (Pi `0.84.2`+), so the meter never moved during an OMP turn; the OMP dialect now lifts it. OMP `18.8.9`'s Anthropic stream sets usage at `message_start`; providers that report usage only at response end move the meter once per assistant message. The lift was checked against the installed binary, not a recorded live stream.
- OMP's `todo` tool shows as the thread's todo list, like Claude's TodoWrite. A successful call reports every phase in `result.details.phases`; the Pi adapter mirrors it into the turn's `todo_list` plan (`ompTodoSteps` in `packages/provider-pi/src/server/rpcDialect.ts`). A `view` call or a failed call leaves the list alone. `in_progress` runs, `completed` and `abandoned` are done, `pending` and `blocked` wait, and tasks carry their phase name when there is more than one phase. Pi has no todo tool, so nothing changes there. Shape checked against OMP `18.9.2` source.
- Thinking streams live for models that think in one unbroken paragraph. Paragraph streaming (the default `responseStreamingMode`) held reasoning until a blank line, list item or closing fence, so the local models behind OMP showed no thought until it ended, even though the Pi adapter received every `thinking_delta`. `apps/server/src/orchestration-v2/assistantStreaming.ts` now passes reasoning's whole text on the existing 400ms throttle for every provider; assistant text keeps paragraph buffering, and `turn` mode still streams nothing.
- Compatible protocol was inspected from installed OMP `18.7.0`; tests cover these adaptations. No model-generation request was used during verification.

## 2. Taiwan Traditional Chinese interface

- Adds `en` and `zh-TW`, a saved device-local language selection, Traditional Chinese browser defaults and English fallback. The General and Appearance settings contain the language selector (`LanguageSettings.tsx`); changing it reloads the page. There is no locale provider: each app's `autoTranslateRuntime` reads the locale once at startup, and on web also sets the document's `lang` and reloads the page when another window stores a different choice.
- Most text is translated at build time so component sources stay identical to upstream. `scripts/i18n/autoTranslate.cjs` runs in the mobile Babel config and, on web, in its own `enforce: "pre"` Vite plugin (`apps/web/vite/autoTranslate.ts`, calling `@babel/core` directly) placed before `react({ compiler: true })`. Variables and default parameters named `tooltip` or ending in `Label`, `Placeholder` or `Tooltip` (`footerActionLabel`, `escapeLabel = "Close"`) are display text in every file, except the agent-facing context-record names below. So is what a render-prop child returns (`<SelectValue>{(value) => value === null ? "Mixed" : LABELS[value]}</SelectValue>`). So are the string values of lookup tables named like `SORT_ORDER_LABELS`, `toolbarTitles` or `MODE_DESCRIPTIONS`, which feed most menu and select options. Helpers whose name ends in `Label`, `Title`, `Placeholder`, `Tooltip` or `Description` (`resolveEnvModeLabel`) return display text, including their local variables; components with such names are excluded. Helpers that build agent context or stored titles (review range labels, plan thread titles, pending-task draft titles) and key names stay English through `untranslated.json`. Mobile follows the device language.
- Files listed in `scripts/i18n/displayFiles.json` build display copy in helpers (provider status summaries, banner titles, update notices, and most mobile screens and `client-runtime` state modules that build error and status text). There, returned values, variable initializers, array elements, `detail`/`details`/`message`/`reason`/`body`/`text`/`error`/`notice`/`statusText`/`warning` properties and capitalized values of constant tables (`const STATES = { open: "Open" }`) are translated too. "Stream failed.")`, `error = "Clipboard is empty."`, `value="Server and provider updates"`). Add a file there when its helper text stays English. Because a display file translates every returned or assigned literal the catalog knows, words that the file uses as identifiers (`"failed"`, `"queue"`, `"image"`, cache-key parts such as `"none"`) are listed for that file in `untranslated.json`; check new catalog words against the display files before adding them. `details` covers the prompt-link landing page's summary lines; a template nested inside a conditional spread is still skipped.

## 3. Local ACP commands in provider updates

- A local ACP command (`source: "local"`) has no registry entry, so its snapshot version is the `agentInfo.version` it reports in ACP `initialize`. Registry agents keep the registry's version.
- Two hidden settings opt it into the existing update flow: `npmPackageName`, used only to look up npm `latest`, and `updateCommand`, an executable and arguments the runner spawns with the instance's environment under a `local:<instanceId>` lock. Without them nothing changes. The command must not prompt: it has no terminal and the runner gives it five minutes.
- After a successful update, upstream's `ProviderRegistry.refreshAfterUpdate` (#14319) calls `invalidateCaches` on every enabled instance of that driver and probes it fresh. The fork only supplies the ACP driver's `invalidateCaches`, which drops its probe cache, so the next probe reads the new version and models; updating one local ACP command also re-probes the other ACP instances. The ACP readiness check repeats the last probed version so health refreshes neither blank it nor miss the probe cache.
- Updates are still started by a person (toast, instance card, mobile); the server never runs them on its own. Web update prompts group by driver, so every local ACP instance is named "ACP Registry" there.
- The maintenance capabilities, the probed version and the npm version advisory live in `packages/provider-acp-registry/src/server/localCommandUpdates.ts`; `driver.ts` calls it from its snapshot pipeline. The advisory is added to a background probe's result before the snapshot permit is taken, so the npm lookup never holds up live command and configuration updates.

## 4. Manual context compaction for ACP agents

- The ACP Registry adapter exposes the existing compaction operation so the context meter can execute an agent's advertised `compact` command. The UI still offers the button only when the agent lists that command, and disables it during a running turn. This also applies to local commands such as `perch-acp`.
- kimi-code (2.3.1) answers `/compact` the moment its compaction starts in the background. A message sent before it ends is queued by kimi's engine and answered at once, so T3 closed the run with no output while kimi ran that turn unseen and dropped its updates (agent-channel #30, 2026-10-24). `packages/provider-acp-registry/src/server/backgroundCompaction.ts` wraps every registry runtime: when a `/compact` prompt reports `Context compaction started`, the prompt stays open until kimi's `Compaction completed.` or `Compaction cancelled.` notice, so the next message waits in T3's queue and the notice shows in the compaction turn. Stop ends the wait as cancelled. kimi sends nothing when the compaction request fails, so the wait gives up after 15 minutes. It keys on kimi's English wording and needs revisiting if kimi changes it; agents that compact before answering are unaffected. Covered by `backgroundCompaction.fork.test.ts`.

## 5. MCP approval codes and remote agent sign-in

- `t3 auth pairing create` takes `--session-ttl <duration>` (how long MCP sign-ins approved with the code last; upstream fixes 30 days and issues no refresh tokens) and `--reusable` (approvals do not spend the code until its own `--ttl` ends or it is revoked). Either flag makes an MCP-only code: device pairing refuses it, so a reusable code can never pair unlimited clients. Plain codes and Settings → Connections codes are unchanged. The flags live in `apps/server/src/cli/authMcpApproval.ts`.
- The options live in the pairing link's `subject` (`mcp-approval;ttl=<ms>;reusable`, `apps/server/src/auth/mcpApprovalCode.ts`) rather than new columns, because a fork migration would collide with upstream's numbered migrations. `McpApprovalCodes.ts` wraps upstream's `PairingGrantStore` layer, and EnvironmentAuth's layer provides it instead: the wrapped `consume` refuses MCP-only codes, and `McpApprovalCodes.use` reads a code for MCP approval without spending a reusable one. `PairingGrantStore.ts` is upstream's. The session TTL travels in McpOAuth's pending authorization code to `issueMcpClientSession`.
- The `/connect-agent` page no longer redirects straight to a loopback callback after approval. It shows **Continue on this computer** and **Copy link**, because an agent such as mcp-remote on the Grok Bot's machine listens on its own `localhost`, which the approving browser cannot reach. Denials and https callbacks still redirect immediately.
- Covered by `apps/server/src/auth/McpOAuth.fork.test.ts` ("an MCP approval code sets the sign-in lifetime, may be reused, and never pairs a client").

## 6. Device sign-ins renew while devices connect

- Upstream fixes direct-paired sessions (bearer tokens and browser cookies) at 30 days; only T3 Connect renews, by minting new DPoP tokens through the cloud, which this fork cannot use. The fork renews the stored session instead: when a session connects with 29 days or less left, `expires_at` moves to now + 30 days (`apps/server/src/auth/sessionRenewal.ts`). It renews in `markConnected` (alongside `lastConnectedAt`), in the WebSocket ticket handler for browser cookies, and in `awaitInvalidation`, which wakes an open connection when its session falls due instead of sleeping until the deadline read at connect time.
- `SessionStore.verify` checks the stored `expires_at` instead of the token's `exp` claim, and returns it. Renewing the row alone would not help: a bearer token is rejected at its claim before it can get a WebSocket ticket. The claim is still decoded and validated, and it equals the stored expiry until a session is first renewed, so unrenewed sessions behave as upstream.
- Browsers drop a cookie at the `Expires` it was set with, so the ticket handler renews first and then re-sets the `t3_session_*` cookie with the stored expiry (`renewBrowserSessionCookie` in `auth/authHttpFork.ts`).
- Never renewed: revoked or expired sessions (the SQL update repeats both guards, so a revocation that races a renewal still wins), `mcp-client` sessions (their lifetime comes from `--session-ttl`, patch 5), DPoP sessions, and sessions issued shorter than 30 days.
- No migration; only the existing `expires_at` column changes. The upstream code touched is the expiry check in `verify`, one line in `markConnected`, the sleep in `awaitInvalidation`, the `renewIfDue` service method (passed through from `sessionRenewal.ts`) and one line in the ticket handler. Sessions issued before this patch renew on their next connection.
- Covered by `apps/server/src/auth/sessionRenewal.test.ts`.

## 7. Tailscale pairing, tagged MCP sign-ins and tailnet discovery

- Off by default. `T3CODE_TAILSCALE_PAIRING=true` turns on device pairing and discovery; `T3CODE_TAILSCALE_MCP_TAGS="tag:x=<access>,…"` turns on MCP approval for those tags. Both are read in `apps/server/src/auth/TailscalePairing.ts`, an env var rather than a `ServerConfig` field so upstream's config and its tests stay untouched.
- The tailnet identity only replaces the pairing code. `POST /api/auth/tailscale-pairing` hands the requesting device a one-minute pairing code (subject `tailscale:<StableID>`, label = machine name, standard scopes), which the client redeems through the existing `/oauth/token` or browser-session exchange, so patch 6 renewal and every later auth and Origin check apply unchanged. Web pages can reach tailnet addresses and a standard session runs terminals, so the endpoint also checks Origin and requires the Host to be an IP, a single-label name or a MagicDNS name: without a code to guard it, DNS rebinding would otherwise pass as same-origin.
- Identity comes from `tailscale whois` on the TCP peer (`request.source.socket.remoteAddress`, never a header). Tailscale Serve reaches the server from the host itself (agent-hub: its own tailnet IP, not 127.0.0.1), and whois on a local address names the host and its owner, so a local peer is never looked up: only Serve's `X-Forwarded-For` is, plus `Tailscale-User-Login` for device pairing. Serve (`ipn/ipnlocal/serve.go`, `httputil.ReverseProxy.Rewrite`) strips client-sent copies of both and omits the user for tagged nodes, funnel and local traffic. Any local process can claim to be Serve; the host is trusted, and no other reverse proxy may front the server while this is on.
- Devices: untagged, owner equal to the host's (`status --json` Self → User), host not tagged. MCP: tagged nodes whose tags are listed get the lowest listed access, only for loopback redirect URIs, so a code issued at `/oauth/mcp/authorize` without the approval page can only reach the requesting machine. Its session subject is `mcp-client:tailscale:<StableID>`; `mcpClientSubject.ts` is now the single check that confines MCP sessions to `/mcp` (EnvironmentAuth's audience check, `authenticateMcpClient`, patch 6's renewal exclusion), and a test fails if the audience check goes back to an exact match.
- Revocation without a migration: a node is blocked when its newest revocation is later than its newest session under that subject. Revocations made by issuing a replacement session (same instant as the replacement's `issued_at`, any subject) do not count, and a node with several clients is blocked by revoking any of them. `t3 auth tailscale blocked|unblock` lifts a block by inserting an already-expired session row, which can never authenticate.
- Discovery: `GET /api/tailnet/servers` (orchestration:read) probes the owner's online, untagged, non-phone peers at `http://<IPv4>:3773` (and the server's own port) and `https://<MagicDNS>/` for `/.well-known/t3/environment`. Clients ask every connected environment (`client-runtime/src/connection/tailnetDiscovery.ts`); mobile can also list devices with a Tailscale OAuth client (`devices:core:read`, client credentials only; Tailscale offers no interactive login for third-party apps), checked against the API before it is kept in SecureStore.
- Clients: an address without a code pairs over Tailscale (`resolveCodelessPairingEndpoint` in `packages/shared/src/remote.ts`, onboarding in client-runtime, mobile `buildPairingUrl`); a rejected or missing saved bearer credential tries it before failing (resolver bearer broker); the web primary tries it before the pairing screen when the server is `remote-reachable` only, so loopback servers make no extra request.
- Upstream code touched: the forbidden reason literal, the `TailnetServer` schema and two endpoints in `contracts/environmentHttp.ts`; two `.handle` lines in `auth/http.ts`, whose handlers live in `auth/authHttpFork.ts` (the service is optional, so routes built without it refuse); one `Layer.provide` in `server.ts`; the authorize redirect in `mcpOAuthHttp.ts`; `McpOAuth`'s pending-code session options and `approveOverTailscale` (built on `approveMcpSignIn` in `TailscalePairing.ts`); `issueMcpClientSession`'s optional subject; the bearer broker, onboarding, web `auth.ts`, the add environment dialog (`AddEnvironmentDialog.tsx`, `parseRemotePairingFields` in `ConnectionsSettings.logic.ts`), mobile pairing screen and `buildPairingUrl`, and the web test helper.
- `packages/tailscale/src/tailnetIdentity.ts` reads host identity, `whois` and peers; `tailscale.ts` only allows the `whois` subcommand and exports `readTailscaleOutput` for it.
- Covered by `TailscalePairing.test.ts`, `TailscaleMcpApproval.test.ts`, `packages/tailscale` identity tests (`tailnetIdentity.test.ts`), client-runtime onboarding, resolver and `tailnetDiscovery` tests, and web `authBootstrap.test.ts`.

## 8. Tailscale dot-matrix T3 fork icon

## 9. Agent browser tabs stay composited while the panel is collapsed

- On the desktop app, a server tab the agent opened (`automationOwner` set) counts as rendering in `HostedBrowserWebview.tsx`, like a recording or picture-in-picture tab: with the panel collapsed its webview sits behind the app at (0, 0) instead of at -100000. `ElectronBrowserHost.tsx` passes the flag in `serverRendering.agentDriven`.
- Why: Electron stops compositing a guest that lies wholly outside the window, and `preview_snapshot` captures the desktop guest through CDP `Page.captureScreenshot`. With the panel collapsed every agent screenshot came back as a blurry low-resolution frame, and `preview_resize` made no difference (agent-channel issue 20, 2026-10-23).
- Cost: an agent-opened tab keeps compositing for as long as it exists. An idle page draws no frames; an animated one keeps the GPU busy behind the app.
- Left alone: `visible` in `preview_status` and `preview_open` reports server stream viewers (`tab.viewers`), which a desktop-hosted tab never has, so it stays false even with the panel open. A collapsed screenshot is 1280 × 800 at 1x, because `MAX_SCREENSHOT_WIDTH` (1280) shrinks the 2x capture (section 12); an open fill panel 480 wide comes back at 960 wide.

## 11. Ephemeral threads

- A thread is ephemeral from `thread.create` on and never switches. It lives in No project, runs on the OMP instance with a model whose `baseUrl` is loopback (`ServerProviderModel.local`), and nothing of it is kept once it ends: deleted by the user, idle for 60 minutes with no running run, its OMP process gone, or found at server startup. Stop aborts the run first; only a Stop whose abort fails ends the process, and with it the thread. The composer toggle (web `EphemeralDraftToggle.tsx`, mobile `EphemeralThreads.tsx`) appears only for a No project draft on OMP with a local model; `canStartEphemeralThread` in `contracts/src/ephemeralThread.ts` decides for both clients, and the server checks again.
- Policy sits in one dispatch wrapper, `server/src/orchestration-v2/EphemeralThreads.ts`, provided through `ThreadManagementService`. Commands are allow-listed: anything not in `UNCHECKED_COMMANDS` or `CHECKED_COMMANDS` is refused, so a command upstream adds later is refused on an ephemeral thread until someone decides otherwise. Refused: fork, handoff, merge back, context transfer, archive, title regeneration, branch or folder changes (the launch may record the Scratch folder it made, once), scheduled or agent-sent messages, and any model outside the thread's OMP instance or not local. MCP never sees them (`mcp/hideEphemeralThreads.ts`), thread search skips them and the message search index never takes their text (`messageSearchIndex.ts`; FTS5 segments keep deleted text until a merge), guest shares are refused in `GuestShareDecider.ts` because guest commands are dispatched without the wrapper, the agent awareness relay sends fixed text, and the title is the first line of the first message with no title model.
- Purge deletes every row naming the thread from columns found in the live schema (`thread_id`, `source_thread_id`, `target_thread_id`, `child_thread_id`, plus `stream_id`/`aggregate_id` in tables with `aggregate_kind = 'thread'`), so tables upstream adds are covered without edits. It removes attachments, terminals and the Scratch folder first, aligns `orchestration_v2_projection_metadata.last_sequence` (otherwise `t3 doctor` refuses to compact), then runs `wal_checkpoint(TRUNCATE)`. The Scratch folder name carries no words from the message.
- `PRAGMA secure_delete = ON` is set for the whole connection in `persistence/Sqlite.ts`. Turning it on only while purging is not enough: streamed message updates leave old row versions in free pages (measured: 30 marker remnants of 40 updates). Cost on a 3.6 GB copy of real data, 30 rounds of streamed writes: median +5.4%, mean +4.7%, WAL bytes +7.4%. Index pages can still hold the bare thread id, never text; only `VACUUM` clears those.
- A client that resumes a shell subscription from its in-memory cursor would miss a purged thread's `thread.deleted`, so `ws.ts` sends a fresh snapshot when the resume crosses a purge (`replayCrossesPurge`). `ThreadFind`'s per-thread scan cache is evicted on purge; its one-minute text cache is not keyed by thread and simply expires.
- OMP (`provider-pi/src/server/ephemeral.ts`) launches like any OMP thread, with every tool, its extensions, plugins and the user's own MCP servers, except: `--session-dir` points at `.omp-sessions` in the thread's Scratch folder, `--no-title`, no T3 MCP, and a settings overlay with `disabledProviders` for every hosted provider, `enabledModels` for the local ones and OMP's memory off, since it writes what it learns to disk. Jason decided on 2026-10-25 that an ephemeral thread keeps no record but otherwise uses OMP normally. Until then it ran `--no-session` with a seven-tool allowlist, fetch, browser and GitHub off, `write`/`edit` held to the Scratch folder and only listed extensions, and the local model could not answer a weather question. `disabledProviders` filters OMP's model registry, so the vision fallback cannot reach a hosted model either; `enabledProviders` does not restrict models (OMP 18.12.6). A throwaway `--no-session` process with the same launch args lists the models before the real one starts, so providers that extensions or other config sources add are disabled too.
- Purge removes the Scratch folder, and with it the session files, subagents' included. In an OMP 18.12.6 RPC run under a scratch `HOME` with a loopback model, the prompt and reply text appeared only in that session file: no `history.db` or `stats.db` was written. Outside it OMP left no text, only a pointer file in `~/.omp/agent/custom-session-files/` holding the session file's path, a `Session exit recorded` line in its log and an empty lock named by the session id; these stay. Files a tool writes outside the Scratch folder are not tracked and stay too, because nothing tells them apart from files the user already had.
- Clients keep nothing on the device: client-runtime's shell and thread caches skip ephemeral threads, web drafts and the prompt stash leave them out of `localStorage` (the stash refuses), and mobile keeps their drafts and queued messages in memory (`state/ephemeral-thread-keys.ts`, kept apart from the shell atoms so storage modules and their tests do not load them). Deleting always confirms that the conversation is erased and cannot be recovered, with no undo. Actions the server refuses are left out where the UI already decides what to show: an ephemeral session reports no fork, rollback or provider handoff (`PiEphemeralCapabilitiesV2`), so both clients drop the fork button and lock the provider; web's thread menus drop settle, title regeneration and archive, the sidebar row's hover action deletes instead of settling (and a settle sweep skips the row), the composer offers only the thread's runtime mode and local models, and rewind and the settle shortcut are off; mobile's row menu keeps arrange, rename and delete, swiping deletes, and the thread settings sheet lists only local models and the current runtime mode. When one ends, web shows a toast and leaves the thread; mobile's thread screen says the conversation ended (`endedEphemeralThreadKeysAtom`, memory only).
- The window title gains （無痕對話） and never names the thread (web `document.title`, desktop `page-title-updated`), and web notifications and iOS Live Activities show the same fixed text. Android adds `FLAG_SECURE` while one is on screen (`T3NativeControls.setSecureWindow`, reference counted) and `IME_FLAG_NO_PERSONALIZED_LEARNING` to the composer. iOS has no keyboard flag for this, and macOS `setContentProtection` is not used.
- Out of scope: oMLX's SSD prompt cache, Voco and Vocotype history, the macOS account, and disk encryption.

## 12. Desktop snapshots capture device pixels

- `preview_snapshot` on a desktop tab sends `Page.captureScreenshot` with no clip and, when the capture is wider than 1280, shrinks it in the tab with `OffscreenCanvas` in an isolated world (`captureDisplay` in `server/src/preview/ServerBrowserPage.ts`). ## agent-hub headless server (2026-10-14)

- The server runs on the owner's dev machine (`agent-hub`, PVE CT, Ubuntu 24.04 x86_64) from this fork's source at the same commit as the Mac nightly client. The client/server gate is the integer `ORCHESTRATION_PROTOCOL_VERSION` compared for equality (`packages/contracts/src/environment.ts`, enforced in `apps/server/src/ws.ts` and `packages/client-runtime/src/connection/compatibility.ts`); semver strings only drive update notices. Installing upstream's `t3` from `t3.codes/install.sh` would put a different version line on the host, so a source build from the fork is what keeps the gate matched.
- `t3 service install` cannot be used for a fork build: `BootService` downloads and validates a pinned release archive for its own version from GitHub Releases (`packages/shared/src/cliRelease.ts` default base URL), and this fork publishes no releases. A hand-written systemd unit is used instead.
- Unit: `/etc/systemd/system/t3code.service`, a **system** unit modeled on the machine's existing `takopi.service` (`User=jason`, `WantedBy=multi-user.target`, `After=network-online.target tailscaled.service`), not a user unit, so it needs no lingering. `ExecStart` runs `node <repo>/apps/server/dist/bin.mjs serve --host <tailnet IP> --no-browser`; the server binds only that tailnet address, never `0.0.0.0`. `PATH` carries `~/.local/bin`, `~/.opencode/bin` and `~/.kimi-code/bin` so provider CLIs resolve, and `NODE_OPTIONS` raises the heap. The unit header carries the rebuild command.
- Install on the host: `npm i -g pnpm@<version> vite-plus@<version>`, matching root `packageManager` and the `vite-plus` catalog entry (12.14.0 and 1.3.0 since 2026-10-22; an older global `vp` still runs but installs against the old version) (for `vp`), clone the fork, then the CI filtered install from `.github/workflows/release.yml`'s `build_bundle` job minus desktop: `vp install --filter=t3... --filter=@t3tools/web... --filter=@t3tools/scripts...`. This skips Electron and the mobile workspace; the resulting tree matches a full install on every structural count that matters.
- A full-monorepo `pnpm install` OOMs Node's default ~2 GB heap during resolution (exit 134). Set `NODE_OPTIONS=--max-old-space-size=8192` for install and build.
- Root `engines.node ^24.13.1` against the host's Node 26 is a warning only; there is no `engine-strict` and no `.npmrc`, so it is not fatal. The server's own range (`>=24.10`) is satisfied.
- The filtered install rewrites `pnpm-lock.yaml` on the host (it re-resolves `@pierre/trees`' `@pierre/theme` peer, swapping 1.1.0 and 2.0.0 between importers), leaving the checkout dirty. That drift blocks the next `git pull` whenever upstream touches the lockfile, so rebuilds start with `git checkout -- pnpm-lock.yaml && git pull --ff-only`. Never commit the host's lockfile back.
- Build: `vp run --filter @t3tools/web build`, then `node apps/server/scripts/cli.ts build` (tsdown bundle plus copying `apps/web/dist` into `apps/server/dist/client`). Run `node apps/server/dist/bin.mjs serve` afterwards; `t3 update` and the background service do not apply to a server run this way.
